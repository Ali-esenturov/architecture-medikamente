# Задание 5. Cutover-план миграции

## 1) Выбор стратегии

**Выбран подход: Parallel run** (старая и новая системы работают параллельно).

Почему это подходит:
1. Сейчас много ручных процессов и файлов, риск ошибок при резком переключении высокий
2. Есть критичные процессы (запись, оплата, уведомления), их нельзя останавливать
3. Parallel run позволяет проверять новую систему на реальных данных и откатиться без остановки бизнеса

Ограничения подхода:
1. Нужно временно вести двойной контур (нагрузка на команду)
2. Нужна аккуратная синхронизация данных и четкие правила «какая система главная»

## 2) Что мигрируем в рамках cutover

Объем MVP:
1. Самостоятельная запись пациента через портал
2. Видимость записей для ресепшена
3. Напоминания за день до приема пациенту и врачу

Системы в контуре:
1. Старая файловая схема (Excel/файлы) — временно как backup-контур
2. Новая MVP-система записи и напоминаний
3. Почтовый/уведомительный канал

## 3) Cutover-план (по этапам)

| Этап | Описание действия | Ключевые задачи | Ответственные | Время/Сроки | Риски и меры по снижению |
|---|---|---|---|---|---|
| 1. Подготовка | Зафиксировать объем MVP и правила перехода | Список процессов, критерии готовности, чек-лист запуска, runbook инцидентов | Техдиректор, бизнес-аналитик, ИТ-админ | Неделя 1 | Риск: размытый scope. Мера: freeze требований на MVP |
| 2. Очистка и маппинг данных | Подготовить данные из Excel/файлов к загрузке | Убрать дубли, нормализовать поля, сопоставить старые/новые идентификаторы | Бизнес-аналитик, ресепшен-лид, ИТ-админ | Неделя 1-2 | Риск: грязные данные. Мера: правила валидации + ручная сверка выборки |
| 3. Техподготовка | Подготовить окружение и доступы | Роли (patient/reception/doctor), права доступа, логирование, мониторинг | ИТ-админ, техдиректор | Неделя 2 | Риск: неверные доступы. Мера: тестовые аккаунты и access review |
| 4. Тестовый прогон (dry-run) | Прогон миграции без влияния на прод | Импорт тестовых данных, проверка сценариев записи/напоминаний, нагрузочный smoke-test | ИТ-админ, бизнес-аналитик, ресепшен | Неделя 3 | Риск: скрытые дефекты. Мера: фикс багов до пилота, повтор dry-run |
| 5. Пилот Parallel run | Запуск на ограниченной группе | 1 филиал или 2-3 врача, доля трафика 10-20%, ежедневная сверка со старой системой | Техдиректор, ресепшен, ИТ-админ | Неделя 4-5 | Риск: рассинхрон данных. Мера: единый мастер записи (новая система), ежедневный reconciliation |
| 6. Расширение трафика | Постепенно увеличить использование новой системы | 20% -> 50% -> 80%, контроль SLA, контроль ошибок и дублей | Техдиректор, ИТ-админ, бизнес-аналитик | Неделя 6-7 | Риск: деградация под нагрузкой. Мера: поэтапное увеличение + лимиты + быстрый rollback |
| 7. Cutover (основное переключение) | Новая система становится основной | Переключить 100% новых записей в MVP, старую оставить только на чтение/архив | Техдиректор, ИТ-админ, ресепшен-лид | Неделя 8 | Риск: сбой в день переключения. Мера: окно переключения, on-call команда, готовый rollback |
| 8. Стабилизация | Подтвердить стабильную работу после cutover | 2 недели мониторинга, закрытие инцидентов, финальная сверка данных | ИТ-админ, бизнес-аналитик, техдиректор | Неделя 9-10 | Риск: отложенные ошибки. Мера: ежедневные отчеты и исправления по приоритету |

## 4) Критические моменты

1. **Миграция данных**: риск потери/дублей. Нужны dry-run, сверки и контрольные отчеты
2. **Период двойного контура**: риск путаницы у сотрудников. Нужны простые инструкции и один мастер-источник для новых записей
3. **День cutover**: риск простоя. Нужны окно переключения, дежурная команда, четкие триггеры отката

## 5) План отката (rollback)

Условия отката (любое из):
1. Критичный сбой записи > 30 минут
2. Потеря/искажение данных, подтвержденное сверкой
3. Массовая ошибка уведомлений

Действия отката:
1. Остановить прием новых записей в MVP
2. Вернуть прием записей в старый контур (Excel/файлы) по заранее подготовленному шаблону
3. Зафиксировать все операции в журнале инцидента
4. После стабилизации выполнить сверку и повторный запуск по решению техдиректора

Ответственные при откате:
1. Команда решения: техдиректор
2. Техническое переключение: ИТ-админ
3. Операционная коммуникация с ресепшеном и врачами: бизнес-аналитик + ресепшен-лид

## 6) Распределение ролей

1. **Техдиректор**: финальное решение по фазам, cutover и rollback
2. **ИТ-админ**: окружение, доступы, мониторинг, переключение
3. **Бизнес-аналитик**: сценарии, сверки, коммуникация, контроль качества процесса
4. **Ресепшен-лид**: операционная проверка записей и напоминаний
5. **Представитель врачей**: проверка расписания и уведомлений со стороны медиков

## 7) Результат

Подход Parallel run дает безопасный переход без резкой остановки текущей работы. Главная идея плана: маленький пилот -> поэтапное расширение -> основное переключение -> стабилизация, с заранее готовым и понятным откатом
