# Задание 6. Движок классификации данных перед загрузкой в DWH

## 1) Что предложено в архитектуре

Смысл решения:
1. Данные сначала попадают в `Raw Landing Zone`
2. Дальше `Classification Engine` определяет класс конфиденциальности, даже если структура меняется и нет разметки
3. По результату данные идут в разные слои хранилища:
- `Quarantine` — непонятные/сомнительные поля
- `Sensitive Zone` — чувствительные данные под строгими правилами
- `Curated Zone` — обезличенные данные для аналитики
- `BI Mart` — только разрешенные витрины

Это и есть набор слоев для аналитики с учетом Privacy by Design.

## 2) Как учитываются неразмеченные и меняющиеся структуры

1. `Schema Detector` отслеживает новые поля и изменения схемы
2. `PII/PHI Detector` ищет персональные и медицинские данные по правилам (regex, словари, NLP)
3. `Classifier Service` присваивает класс: `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `PHI`
4. `Tagging & Metadata Registry` добавляет метаданные: владелец, цель обработки, срок хранения
5. Если поле не распознано надежно, оно идет в `Quarantine`, а не в аналитическую витрину

## 3) Метрики эффективности классификации

Основные метрики:
1. `Precision` — сколько найденных чувствительных полей реально чувствительные
2. `Recall` — какую долю чувствительных полей мы действительно нашли
3. `F1-score` — общий баланс precision/recall
4. `False Positive Rate` — как часто ошибочно помечаем обычные данные как чувствительные
5. `False Negative Rate` — как часто пропускаем чувствительные данные
6. `Classification latency` — время классификации одного батча
7. `Schema drift detection rate` — как быстро и часто ловим изменения структуры
8. `Quarantine ratio` — доля данных, ушедших в карантин (должна снижаться после настройки правил)

Как это помогает оптимизации:
1. Если высокий false negative — усиливаем правила/модель (безопасность)
2. Если высокий false positive — уменьшаем лишние блокировки (скорость и удобство)
3. Если растет latency — масштабируем воркеры и партиционирование
4. Если растет quarantine ratio — улучшаем правила для новых источников

## 4) Масштабирование и расширение

Для масштабируемости:
1. Обработка батчей через очередь задач
2. Горизонтальное масштабирование воркеров классификации
3. Партиционирование данных по источнику/дате/домену
4. Разделение хранилищ по слоям (quarantine/sensitive/curated/mart)

Для роста объема данных и пользователей:
1. Добавлять новые коннекторы источников без изменения ядра
2. Версионировать правила и модели классификации
3. Держать отдельные профили политик по доменам (мед, финансы, операции)
4. Использовать кэширование и инкрементальную обработку для повторных загрузок

## 5) Дополнительные меры (кроме слоев)

1. Аудит всех классификационных решений и изменений правил
2. RBAC/ABAC доступ к зонам хранения и витринам
3. Маскирование/токенизация/псевдонимизация до попадания в `Curated Zone`
4. Автоматические алерты при аномалиях (резкий рост PHI, рост ошибок классификации)

## 6) Итог

Решение закрывает ключевую проблему: данные на входе неразмеченные и меняются по структуре. Движок классифицирует их до загрузки в аналитическое хранилище, а многослойная схема хранения не дает чувствительным данным попасть в открытую аналитику без нужной обработки и контроля
